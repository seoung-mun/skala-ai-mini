# ADR-0011: 지연을 줄이려고 KURE를 fp16으로 올리고, 필요 없는 검색·리랭킹을 건너뛴다

- 상태: Accepted
- 관련: `src/finagent/retrieval.py`, `graph/agents.py::r_search`, [ADR-0006](0006-hybrid-retrieval-rerank.md), [ADR-0010](0010-local-llm-memory.md)

## 배경
v2는 정답률 87.5%(v1 60.0%)를 얻었지만 지연 중앙값이 11.3초에서 24.5초로 늘었다. 쉬운 질문 4개를 나눠 재 보니 검색 단계가 평균 약 20초였다.
Ollama를 내리면 같은 검색이 약 0.1초라서, 원인은 연산량이 아니라 메모리 경합이다. 16GB에서 Ollama(약 6GB)와 같은 프로세스의 KURE(fp32)·리랭커가 번갈아 서로를 스왑으로 밀어낸다.

## 결정
1. **KURE-v1을 fp16으로 로딩한다.** 리랭커와 같은 방식이다. 임베딩 캐시 키에 dtype을 넣어(`nlpai-lab/KURE-v1@float16`) 정밀도가 다른 벡터를 섞지 않는다. 캐시는 한 번 다시 만든다(문서 910개, 약 9.5초).
2. **상품명이 정확히 매칭되면(`product_ids`가 있으면) rag 서브에이전트가 검색을 생략한다.** 이때 허용 집합이 곧 `product_ids`라서 검색 결과는 그 부분집합이다. `r_select`는 `product_ids`를 앞에 두므로 검색을 해도 결과가 같다(동작 보존).
3. **RRF 후보가 k개 이하면 리랭킹을 생략한다.** 반환되는 집합은 같고 순서만 달라질 수 있다.

## 근거(실측, 2026-10-20, qwen3:8b · num_ctx 8192 · 16GB 노트북)

**fp16 정확성:** 문서 벡터 코사인(fp16 대 기존 fp32 캐시)의 최소값은 0.99975, 평균은 1.0000이었다. 표현 변형 질문 3개에서 dense 상위 50위가 50/50 같았고, 상위 5위 순서도 같았다.

**메모리 (KURE만 단독으로 띄움):**

| | 파라미터 | MPS 할당 | 질의 인코딩 |
|---|---|---|---|
| fp32 | 2,166MB | 3,051MB | 22ms |
| **fp16** | **1,083MB** | **1,129MB** | 18ms |

**누적 ablation (쉬운 질문 E1·N2·S2·N8, Ollama를 올린 상태, 각 1회, 4문항 평균):**

| 변경 | 검색 ms | 총 지연 s | 스왑아웃 페이지 |
|---|---|---|---|
| 변경 전 | 19,670 | 40.7 | 3.10M |
| + KURE fp16 | 7,811 | 24.1 | 1.68M |
| + 상품명 매칭 시 검색 생략 (1회차 / 2회차) | 7,505 / 6,458 | 36.2 / 21.4 | 2.62M / 1.39M |
| + 후보 ≤ k면 리랭킹 생략 | 7,719 | 31.1 | 2.47M |

- 상품명 매칭 시 검색 생략 이후 E1·N2의 검색은 0ms다. 검색 평균은 S2·N8 두 문항이 만든 값이다.
- 리랭킹 생략은 이 4문항에서 발동하지 않는다(허용 후보가 4개 이상). 마지막 줄의 차이는 측정 잡음이다.
- 마지막 측정에서 S2·N8의 검색은 인코딩 약 7.7초와 리랭킹 약 7.6초로 나뉘었다. 둘 다 Ollama 호출 직후라 스왑인 비용이다.
- 측정 중 시스템 스왑 사용량은 12.7GB에서 20GB까지 올라갔다(브라우저 등 다른 앱 포함). 같은 설정을 두 번 재도 총 지연이 21~36초로 흔들렸다. 4문항 ablation은 방향만 보고, 효과는 아래 전체 측정으로 판단한다.

**전체 골든셋 (40문항 × 1회):**

| 지표 | v2 (변경 전) | v2 (변경 후) |
|---|---|---|
| 정답률 | 87.5% | **92.5%** |
| 지연 중앙값 / p90 | 24.5초 / 37.0초 | **13.4초** / 38.8초 |
| 상품명 매칭 문항 19개 지연 중앙값 | 25.9초 | **10.6초** |
| 검색이 필요한 쉬운 질문 8개 지연 중앙값 | 32.6초 | 34.1초 |
| 그 밖의 문항 13개 지연 중앙값 | 11.9초 | 12.5초 |
| 생성 토큰 / 문항 | 188 | 164 |

- 리랭킹이 생략된 문항은 N1·N9(허용 후보 3개)다. 둘 다 정답을 유지했고, 지연은 30.6초에서 17.2초, 24.7초에서 15.6초로 줄었다. N1은 근거 순서만 바뀌었다.
- 정답률 +5%p(S1·S3가 오답에서 정답)는 이번 변경 때문이 아니다. 두 문항의 근거 문서는 전후가 같다.
  - S1은 첫 생성이 바로 검증을 통과했다(이전에는 검증 2회 실패 후 대체 답변).
  - S3는 "최고 연 6.0%"와 "최고금리 6.70%"를 함께 말해, 첫 주장 값 기준으로 정답 처리됐다.
  - temperature 0이어도 생기는 실행 간 변동으로 본다. "정답률이 떨어지지 않았다"까지만 주장한다.

## 대안 비교
| 대안 | 장점 | 단점 |
|---|---|---|
| **A. KURE fp16 (채택)** | MPS 할당 -1.9GB. 벡터는 사실상 같음(코사인 ≥ 0.9997) | 캐시 재생성 1회. 로딩 순간 CPU 상주 메모리가 잠깐 오름(단독 측정 최대 RSS 3.5GB) |
| **B. 상품명 매칭 시 검색 생략 (채택)** | 결과가 같음이 코드로 보장됨. 검색 모델을 깨우지 않아 LLM도 덜 밀려남. 40문항 중 19개에 해당 | 상품명 매칭 규칙이 틀리면 검색 보완이 없음. 이전에도 허용 집합이 product_ids라 같은 한계였음 |
| **C. 후보 ≤ k면 리랭킹 생략 (채택)** | 반환 집합이 같음. 40문항 중 2개가 해당 | 근거 순서가 RRF 순서로 남음. 프롬프트 속 문서 순서가 답에 영향을 줄 수 있음(이번 측정에서는 변화 없음) |
| D. 검색 모델을 CPU로 | GPU 경합 제거 | 실측 19.4초로 효과 없음(메모리 경합이 원인) |
| E. 인용(citations)을 조건 질문에서만 생성 | 생성 토큰 감소(문항당 약 9초가 생성) | 계약의 `citations`를 UI가 근거로 보여 줌. 스키마에 이미 "없으면 빈 배열"이 있어 추가 이득이 불확실함. 채택하지 않음 |
| F. 리랭커 끄기 (`RERANK=0`) | 메모리 약 1.1GB 절약 | S4·N7 top-1 회귀(ADR-0006). 채택하지 않음 |

## 결과·트레이드오프
- 중앙값 개선은 거의 전부 B에서 나왔다. 상품명이 맞은 질문은 검색 모델을 건드리지 않아, LLM 호출도 스왑에 덜 밀린다.
- 검색이 꼭 필요한 표현 변형 질문은 여전히 30초대다. p90(38.8초)은 나아지지 않았다. KURE+리랭커(fp16 합계 약 2.2GB)와 Ollama 6GB가 여전히 번갈아 스왑된다.
- fp16의 메모리 이득은 확실하다. 다만 이번 전체 측정은 시스템 스왑이 20GB까지 찬 상태여서, 지연 이득이 측정 잡음에 묻혔다.

## 재검토 조건
- p90을 줄여야 하면 아래 중 하나를 같은 골든셋으로 측정한다.
  1. 검색 모델을 별도 프로세스에 상주시키거나 Ollama 임베딩으로 옮긴다.
  2. 메모리가 넉넉한 환경을 쓴다.
  3. `LLM_BACKEND=openai`로 바꾼다.
- 상품명 매칭이 부분 일치로 바뀌어 `product_ids`가 넓어지면 B의 "결과 동일" 근거가 깨진다. 이때는 검색 생략 조건을 다시 본다.
